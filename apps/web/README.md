# Web app

Next.js App Router frontend for fin. The workspace package is `@fin/web`; the root README describes the complete local stack and Supabase setup.

## Start

From the repository root, create `.env` from `.env.example`, start local Supabase, copy its URL and `anon` key into the `NEXT_PUBLIC_SUPABASE_*` variables, apply migrations, then run:

```sh
pnpm web
```

Open <http://localhost:3000>. `pnpm --filter @fin/web dev` is the equivalent package-scoped command. The Next config loads the root `.env`; do not duplicate it under `apps/web`.

Useful commands from the repository root:

```sh
pnpm --filter @fin/web build
pnpm --filter @fin/web lint
pnpm --filter @fin/web typecheck
```

Typecheck runs `next typegen` before TypeScript because route/layout prop types are generated by Next. The app also depends on `@fin/shared` and `@fin/db` through workspace links.

## Structure

- `src/app/(auth)/`: signup, login, password reset and MFA verification screens/actions.
- `src/app/(app)/`: authenticated finance screens; feature mutations live beside their route in `actions.ts`.
- `src/app/api/`: data export and the protected FX-rate cron endpoint.
- `src/app/auth/`: Supabase email confirmation and OAuth callback routes.
- `src/lib/supabase/`: browser/server clients and cookie/session refresh.
- `src/components/i18n-provider.tsx` and `src/lib/i18n.ts`: locale context for React, server locale resolution and localized metadata. The profile's regional locale selects Spanish/English; a secure cookie keeps it available on public/auth pages.
- `src/proxy.ts`: refreshes the Supabase session on requests. The private route layout independently verifies the user before rendering.

Read [route and flow documentation](src/app/README.md), [service boundaries](src/lib/README.md), and the [architecture overview](../../docs/architecture.md) before changing authentication, money calculations, or data access.

## Configuration and security

`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `NEXT_PUBLIC_SITE_URL` are public configuration. `DATABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `CRON_SECRET` are server-only; never prefix secrets with `NEXT_PUBLIC_` or expose them to client components. Google sign-in stays hidden unless `NEXT_PUBLIC_GOOGLE_AUTH_ENABLED=true` and the Supabase provider is configured.

Most authenticated data access uses a cookie-bound Supabase server client and the user's JWT, so Postgres RLS remains authoritative. Keep admin/service-role access limited to server-only operations that need it.
